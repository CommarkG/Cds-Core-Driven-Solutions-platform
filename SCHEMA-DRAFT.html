CDS Vocabulary Schema

Master schema defining how vocabulary terms relate, interconnect, and organize.

⚠️ CRITICAL: This schema must be ratified before populating vocabulary with content. No term can be added to the Vocabulary page without conforming to this schema structure.
---

1. Core Principle: Vocabulary Terms Are Interconnected

Every vocabulary term in CDS does not exist in isolation. Each term:

  • Belongs to a group (e.g., Process, Artifact, Actor, Pattern)
  • Has a definition (context + good examples + bad examples)
  • References other terms (relationships / dependencies)
  • Has a role (what it does in the system)
  • Has a tag (status, type, classification)
  • Has wiring (how it connects to other components)
  • Has update rules (how it evolves, when it can change)
---

2. Schema Structure: Seven Core Dimensions

Every vocabulary term MUST be defined across these seven dimensions:

Dimension Definition Example (for "Template")
Group Which vocabulary group does this term belong to? (e.g., Artifact, Process, Actor, Pattern) Artifact (reusable structure)
Definition Context + purpose + 2 good examples + 2 bad examples + measurements A repeatable structure that can be duplicated with all code + wiring inside
Core Hierarchies What does this term contain? (parent-child relationships) Template contains: Elements, Variants, Wiring, Tests
Relationships What other terms does this reference? (Role / Dependencies / Serving) Template uses: CoreSpine, Pattern, Tag, Status
Wiring How does this connect to the system? (mechanical connections) Template wired to: Git, Schema, Checklist, CI/CD gates
Updating How/when can this change? (rules + authority) Template: can evolve in SCOPE 1/2, locked in CORE. Yariv approval for breaking changes.
Tag/Status Current state + classification (from Tags & Statuses page) Status: ACTIVE | Tag: HARDWIRED_STRUCTURE

5. Term Relationships: Four Types

Relationship Type Definition Example
Hierarchy Parent-child containment (X contains Y) Template contains: CoreSpine, Variants, Elements
Dependency X requires Y to function (X depends on Y) Mechanical Hardcoding depends on: Schema, Checklist, Linter
Reference X uses Y as input/context (X references Y) CoreSpine references: Template, Pattern, Tag, Status
Serving X enables/supports Y (X serves Y) CoreSpine serves: Template instantiation, infinite scaling
---

6. Wiring: How Terms Connect Mechanically

Every term must specify its mechanical wiring:

  • Schema Nodes: What schema.yaml nodes does this term map to?
  • Git Integration: How is this stored/tracked in git?
  • Checklist Gates: What checklist items verify this?
  • CI/CD Enforcement: What pre-commit hooks / linters enforce this?
  • Authority Approval: What level of approval is required to change this?
  • Audit Trail: How is change history tracked?
Example — Wiring for "Template": - Schema Nodes: decisions.template, decisions.core_spine - Git: Stored in /templates/{name}/, versioned - Checklist: Template Verification Checklist (250+ items) - CI/CD: Pre-commit hook validates template structure - Authority: CORE templates locked, SCOPE 1/2 can evolve. Breaking changes require Yariv approval. - Audit: All template changes logged in git with decision-log references

7. Status & Tag System

Every term has a Status (current condition) and Tags (classification):

Status Values (mutually exclusive):

  • ACTIVE — Currently used, fully implemented
  • PENDING — Approved but not yet fully implemented
  • DRAFT — Proposed, awaiting approval
  • BLOCKED — Waiting on external dependency
  • ARCHIVED — No longer used, retained for history

Tag Examples (can have multiple):

  • HARDWIRED — Mechanically enforced, cannot be bypassed
  • TEMPLATE — Reusable structure
  • DESIGN — UX/UI component
  • PROCESS — Repeatable workflow
  • GOVERNANCE — Authority/approval required
  • SCHEMA — Part of canonical schema
  • METHODOLOGY — Core approach/practice
---

8. Updating Rules: When & How Terms Evolve

Every term has rules about how it can change:

Category CORE (Phase 1) SCOPE 1 (Phase 2-3) SCOPE 2+ (Future)
Name Changes ❌ Locked. No changes. ⚠️ Yariv approval only. Creates alias. ✅ Can evolve, tracked as variant
Definition Changes ❌ Locked. No changes. ⚠️ Yariv approval. Must update all references. ✅ Can evolve gradually
Adding Sub-elements ⚠️ Yariv approval only ✅ Can add in SCOPE 1, approved by CDS ✅ Can add freely
Removing Elements ❌ Never remove from CORE ❌ Never remove, only deprecate ✅ Deprecate, migrate, then remove
Breaking Changes ❌ No breaking changes ⚠️ Requires Yariv approval + migration plan ✅ Documented deprecation path
---

9. Vocabulary Completeness Checklist

Before a term is considered "complete" and can be used, verify:

  • ☐ Group assigned (and group exists in schema)
  • ☐ Definition includes: context + 2 good examples + 2 bad examples + measurements
  • ☐ Core hierarchies documented (what it contains, what contains it)
  • ☐ All relationships documented (role, dependencies, serving, references)
  • ☐ Wiring specified (schema nodes, git path, checklist gates, CI/CD enforcement)
  • ☐ Updating rules clear (authority, evolution path, breaking change policy)
  • ☐ Status + Tags assigned
  • ☐ Related terms cross-linked (in Vocabulary page)
  • ☐ Yariv approval (if CORE or breaking change)
---

10. Reading This Schema

When you see a term on the Vocabulary page, you should be able to:

  1. Understand what group it belongs to
  2. Read its definition with examples
  3. See what other terms it relates to
  4. Understand how it mechanically connects to the system
  5. Know the rules for changing it
  6. See its current status
