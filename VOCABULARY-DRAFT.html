GROUP 1: ARTIFACTS — Reusable Structures

Tangible things created and reused. Repeatable, versioned, stored in git.

Template

Template
Group
Artifacts
Status
ACTIVE
Tags
HARDWIRED_STRUCTURE DESIGN CORE

Definition: A repeatable structure that can be duplicated as-is with all code + wiring + connections inside. Templates define how similar features are built consistently.

Good Examples:

  • Dashboard Template: title + filters + table + export + actions
  • Workflow Template: intro + steps 1-N + review + confirmation

Bad Examples:

  • A generic "component library" without wiring or context — just UI, no system integration
  • A documented process without executable code — guidelines instead of templates

Core Hierarchies: Template contains Elements, Variants, Wiring, Tests, Documentation

Relationships:

  • Role: Enables infinite feature scaling by providing verified blueprint
  • Dependencies: Depends on Schema, Checklist, Pattern
  • Serving: Enables instantiation of new features, maintains consistency
  • References: CoreSpine, Pattern, Tag, Status

Wiring: Stored in /templates/{name}/, versioned in git. Validated by Template Verification Checklist. Pre-commit hook checks structure before commit.

Updating: CORE templates locked (no changes). SCOPE 1/2 can evolve. Breaking changes require Yariv approval.

CoreSpine

CoreSpine
Group
Artifacts
Status
PENDING
Tags
TEMPLATE REUSABLE

Definition: The hardwired repeatable structure of a type of feature. One CoreSpine = infinite instances. Example: Dashboard CoreSpine defines title+filters+table structure that all dashboards follow.

Good Examples:

  • Dashboard CoreSpine: All participant dashboards, bundle dashboards, metrics dashboards use the same structure
  • Workflow CoreSpine: Goal Wizard, onboarding, approval flows all follow intro-steps-review-confirm pattern

Bad Examples:

  • One-off dashboard built without CoreSpine — inconsistent with others
  • Process documented in Notion but not wired to code or schema

Core Hierarchies: CoreSpine contains: Layout Rules, Component Slots, Wiring Rules, Data Schema

Relationships:

  • Role: Master pattern that scales infinitely
  • Dependencies: Depends on Schema, Checklist, Pattern
  • Serving: Serves all instances of that feature type
  • References: Template, CoreCycles, CoreCouncil

Wiring: Documented in CDS-OPTIONS-LIBRARY-FRAMEWORK.md. Referenced by Template. Enforced via checklist.

Updating: CoreSpine can evolve in SCOPE 1/2, locked in CORE. Must maintain backward compatibility.

GROUP 2: PROCESSES — Repeatable Flows

Repeatable sequences of actions. How work gets done, how decisions are made, how progress is tracked.

Flow / Pipeline

Flow / Pipeline
Group
Processes
Status
ACTIVE
Tags
DESIGN UX

Definition: Sequence of steps to accomplish a goal.

  • Flow: User-facing process (Goal Wizard, configuration)
  • Pipeline: System/backend process (data ingestion, processing)

Good Examples:

  • Goal Wizard flow: Intro → Steps → Review → Confirm
  • Conflict escalation pipeline: Detect → Triage → Escalate → Resolve

Differences & Best Use:

  • Flow: When users interact directly. Design with UX, wireframe, test with users.
  • Pipeline: When system processes internally. Design with logic, test with data, monitor with metrics.

Relationships: References Template (wizards, forms), Pattern (interaction design)

Group

Mechanical Enforcing / Accountability

Mechanical Enforcing / Accountability
Group
Methodology
Status
ACTIVE
Tags
HARDWIRED GOVERNANCE

Definition: Making rules impossible to violate (mechanical) instead of hoping people follow them (accountability).

Difference:

  • Accountability: "You are responsible for following this rule" (depends on person)
  • Mechanical Enforcing: "This rule is impossible to violate" (depends on system)

Example: Instead of "document your decisions," use immutable decision-log wired to approval gate. Impossible to ship without documentation.

GROUP 8: QUALITY ASSURANCE — How We Verify

Activities that ensure quality and correctness.

QC / Sanity Check / Review / Validation / Verification / Audit / Deep Dive

QC / Sanity Check / Review / Validation / Verification / Audit / Deep Dive
Group
Quality Assurance
Status
ACTIVE
Tags
VERIFICATION GOVERNANCE

Definitions & Differences:

  • QC (Quality Control): Automated checks. Did code compile? Do tests pass? Schema valid?
  • Sanity Check: Quick manual verification. Does this obviously work? Are there obvious errors?
  • Review: Code review. Does code follow patterns? Is logic sound? Is it maintainable?
  • Validation: Does it meet the specification? (Correctness against spec)
  • Verification: Does it work? (Functional correctness)
  • Audit: Full compliance check against all standards. Every checkbox verified.
  • Deep Dive: Exhaustive analysis. Every edge case, every interaction, every assumption tested.

Usage Flow: QC → Sanity Check → Review → Validation → Verification → Audit (for critical paths) → Deep Dive (for major releases)

Wiring: QC is pre-commit hook (mechanical). Review is PR process (human). Validation is checklist. Verification is testing. Audit is comprehensive checklist. Deep Dive is manual exploration.

GROUP 9: DESIGN & UX — Visual/User Layer

Visual design and user experience elements.

UX / UX Element / UI / UI Element

UX / UX Element / UI / UI Element
Group
Design & UX
Status
ACTIVE
Tags
DESIGN CORE

Definitions & Differences:

  • UX (User Experience): How users interact with the system. Flows, workflows, decision points, information architecture.
  • UX Element: Reusable interaction component (button state, form validation, navigation pattern)
  • UI (User Interface): What users see. Visual design, layout, colors, typography, spacing.
  • UI Element: Reusable visual component (button, input, card, modal)

Relationship: UX is about behavior. UI is about appearance. Both matter. UI implements UX. UX specifies what UI must support.

Good Example:

  • UX: Form has validation feedback before submission
  • UI Element: Error message shown in red box below input

Wiring: UX defined in wireframes + flows. UI defined in design tokens + component library. Both verified by checklist.
